## 2. 故障清单（按类别）

### A. 链接与数据类

**A-1 知乎软 404（8/27 修复，8/31 复发）**
- 现象：推送的知乎链接打开是"404 - 知乎"页。
- 根因：知乎 API 返回 `api.zhihu.com/questions/{id}`（复数路径），网页端标准路径是单数 `question/{id}`；复数路径返回 HTTP 200 + "404" 页面。
- 排查难点：**HTTP 状态码全是 200**，curl 查状态码看不出问题，直到抓页面内容才发现是软 404。
- 复发教训：修复后**常驻服务未重启**，旧代码继续跑 4 天，坏链接从 51 条累积到 84 条（见 B-1）。
- 修复：URL 单数化 + 存量批量修正（两次共 135 条）。
- 教训：**外部 API 的返回格式要以网页端实测为准，不能想当然**；HTTP 200 ≠ 内容正确。

**A-2 hnews 链接指向官网主页（9/1）**
- 现象：【Hacker News】条目"Launch HN: Almanac"链接指向 usealmanac.com 主页。
- 根因：Algolia API 的 `url` 字段对 Launch HN 帖子返回项目官网（非文章页），适配器"url 非空即用"。
- 修复：hnews 一律链接 HN 讨论页 `item?id=`（语义与来源标注一致，页面自带原文）。
- 教训：**来源标注与链接语义必须一致**；聚合类源（HN/Reddit 风格）应链回讨论页而非原文站。

### B. 部署与流程类

**B-1 改代码不重启服务，旧代码跑 4 天（8/27–8/31）— 最贵的一次**
- 现象：知乎修复后推送链接仍坏。
- 根因：`daily-picks.service` 是 APScheduler **进程内调度**，模块在启动时加载；修复后误判"无需重启"，线上继续跑修复前代码。
- 影响：84 条坏链接入库（超初修 51 条）、用户连续 3 天看到坏链接。
- 修复：存量二次修正 + AGENTS.md 第 7 条硬规范（**改任何 daily_picks/ 或 worker/ 代码必须 `systemctl --user restart daily-picks.service`**）+ 设计文档 §16.3 事故留档。
- 教训：**常驻进程的代码更新 = 改代码 + 重启，两步缺一不可**；"本地验证通过"不等于"线上生效"。

**B-2 worker/.wrangler 本地缓存误提交（9/1）**
- 现象：wrangler 账号缓存（含 Cloudflare 账号信息）进了 git。
- 根因：`git add -A` 未排除 wrangler 运行产物。
- 处理：`git rm --cached` + .gitignore 补 `worker/.wrangler/`；检查历史残留（仅账号 ID，无凭据，低危）。
- 教训：**部署类 CLI 的本地产物要提前入 .gitignore**；提交前用 `git status` 过目新增文件。

### C. 配置与功能类（"写了但没接线"三连）

**C-1 digest.min_score 配置未生效（8/31）**
- 现象：config 配了 min_score 阈值，行为无变化。
- 根因：配置项在 `config.py` 定义、示例文档有注释，但 **ranker 从未读取**。
- 修复：`select_candidates` 加参数并接线。
- 教训：**配置键的"定义"和"消费"要同时完成**；测试应覆盖"配置值确实改变行为"（现在有 T-RANK-13 系列）。

**C-2 source_registry 只写不读（M10 遗留，9/1 发现）**
- 现象：setup 向导选的源（如"创业商业"推荐 36氪/虎嗅）实际从不被采集。
- 根因：setup 把推荐源 key 写进 user_profile 和 registry，但**采集侧 `build_adapters` 只读 config.yaml 的 rss.urls**，registry 无消费者。
- 修复：`build_adapters(cfg, storage)` 合并 registry urls；RssAdapter 支持 extra_urls。
- 教训：**写路径和读路径必须成对出现**；新数据表/配置项上线时要问"谁在读它"。

**C-3 内置推荐指向已失效的 RSS（9/1）**
- 现象：机器之心/36氪/虎嗅的公开 RSS 早已关闭（返回 HTML/404），setup 仍推荐、TAG_SOURCE_MAP 仍列出。
- 根因：内置源清单是**静态编写**的，从未实测验证；LLM 推荐的 6 个"一人公司"源同样全灭（A 类问题的延续）。
- 修复：TAG_SOURCE_MAP 只保留实测有效的源；新增 SOURCE_URLS 并**先 curl 验证再入库**；文档标注。
- 教训：**国内内容平台的公开 RSS 大面积关闭是常态**；内容源清单必须"实测可用才进推荐"，LLM 输出（含 URL）必须验证——LLM 会自信地给出 404 地址。

### D. LLM 输出类（"LLM 不可信"三案例）

**D-1 思维链吃光 max_tokens，输出为空（M2）**
- 现象：LLM 精排偶发返回空 → 静默降级规则分。
- 根因：deepseek-v4-pro 是思考模型，2000 token 上限被思维链耗尽，`content` 为空。
- 排查特征：成本 > 0 但输出空、tokens_out == max_tokens。
- 修复：max_tokens 2000→8000（代码/配置/文档三处同步）+ 校验失败诊断日志。
- 教训：**思考模型的 max_tokens 预算要按"思维链+答案"估算**；三处（代码默认/示例配置/文档）会独立漂移，改一处不够。

**D-2 deep 关键词与推荐理由编造（9/4，用户发现）**
- 现象：推送关键词（"上下文窗口/外部记忆"）和理由（"剖析了 XX 瓶颈"）在原文中找不到。
- 根因：deep_analyze 只喂 title + 73 字摘要，**从不读全文**；信息不足时 LLM 基于标题联想编造看似具体的细节。
- 修复（三层）：
  1. 摘要 <200 字时**自动抓正文**前 3000 字喂给 LLM（基于真实内容分析）；
  2. Prompt 反编造约束（"关键词必须直接来自原文，禁止联想未提供的信息"）；
  3. **代码侧可验证校验**——关键词逐词在原文检索，不在原文的剔除（全编造 → 摘要兜底，宁缺毋滥不误导）。
  4. deep 结果落库（digest_items 加 deep_* 列），以后每条推荐可回查。
- 教训：**LLM 生成的内容必须"可验证"**——要么喂足上下文，要么输出能对原文校验；摘要太短时 LLM 编造是必然不是偶然。

## 3. 共性根因（6 条，按杀伤力排序）

1. **"本地/单点验证通过"≠"系统真实生效"**（B-1 最贵、C-1/C-2）——配置、代码、服务三者的"接线"缺少端到端验证。杀伤力最高，因为影响面是"静默持续错误"。
2. **对真实世界假设过强**（A-1 知乎路径、A-2 链接语义、C-3 国内 RSS、B-1 隐含的 workers.dev 可达性）——外部系统（API 格式、URL 有效性、域名可达性）必须实测，且**要周期性复测**（RSS 会死、域名会被墙）。
3. **LLM 输出不可信**（D-1 空输出、D-2 编造）——必须校验 + 降级 + 可审计。
4. **"写了但没接线"**（C-1/C-2）——配置键/数据表的定义与消费不成对。
5. **测试覆盖的是"代码路径"而非"真实故障"**（软 404 骗过 curl、mock 测不出真幻觉、服务没真实启动过）。
6. **文档与实现漂移**（max_tokens 三处、测试命令、编号撞号）——一处事实多处记录，必有一处过期。

| 机制 | 防的故障 |

| 隐私：.gitignore 补部署产物；提交前 git status 过目 | B-2 |

## 5. 遗留建议（未实施，按优先级）

1. **内容源健康检查**：`daily-picks test sources` 定期（每周）实测各源 url 可达性并告警——RSS 会死是常态，需要周期性复测（对应共性根因 2）。
2. **配置生效自检**：`daily-picks test config` 校验"每个配置键都有消费方"（对应根因 1/4，C-1/C-2 这类问题一次排查到位）。
3. **真实环境 smoke 自动跑**：每日推送后校验推送内容格式 + 链接 HTTP 状态（软 404 检测：不只查状态码，抓内容查 404 标记）。
4. deep prompt 变更后的人工抽查：LLM 行为改进要靠真实推送反馈验证，建议每周人工抽查 1 次关键词与原文匹配度。
